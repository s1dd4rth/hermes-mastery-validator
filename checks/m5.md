# Module 5 — Skills (Pillar 3)

Run: `node bin/verify.js 5`

## Deterministic checks

| ID | What it verifies | How |
|---|---|---|
| `at-least-one-installed-skill` | `~/.hermes/skills/` contains at least one skill directory (with `SKILL.md`) that is **not** `hermes-mastery-validator` itself | `fs.readdirSync`, filter out `.`-prefixed dirs, drop validator slug, check `SKILL.md` exists |
| `at-least-one-custom-skill` | At least one installed skill is user-created: NOT in the bundled-skills allowlist AND NOT in the hub-known allowlist AND has no `_meta.json` (Hermes writes `_meta.json` for hub-installed skills) | Same skill set as above, minus bundled + hub-known + `_meta.json`-present entries |

## Manual check

- `skills-fresh-session` — Start a fresh session (`hermes /new` or equivalent) and verify both your hub-installed skill and your custom skill load. If the custom skill doesn't surface, it didn't really get created.

## Self-exclusion guard (spec §13)

`at-least-one-installed-skill` explicitly excludes `hermes-mastery-validator` from the count. This prevents the degenerate case where a learner installs *only* the validator skill and passes M5 with zero learning.

## Bundled-skills allowlist (locked 2026-05-28)

These skills ship with `hermes setup` out-of-box. They are NOT user-created and do NOT count toward `at-least-one-custom-skill`.

```js
const M5_BUNDLED_SKILLS = [
  'dogfood',
  'yuanbao',
];
```

**How these were determined:**

1. Enumerated `~/.hermes/skills/` on the dev box — 24 directories plus the `hermes-mastery-validator` symlink.
2. Checked for `_meta.json` presence: Hermes writes `_meta.json` when a skill is hub-installed via `hermes skills install`. All 24 directories had NO `_meta.json` — none were hub-installed at build time.
3. Cross-referenced against `~/.hermes/skills/.bundled_manifest` (Hermes-internal slug:hash file). Only `dogfood` and `yuanbao` matched top-level directory names with `SKILL.md` at their root.
4. All other directories (`apple`, `creative`, `devops`, etc.) are **category folders** — they contain nested skills but have no `SKILL.md` at their own root. They are filtered out by the `withSkillMd` step before the bundled/custom classification runs.

## Hub-known allowlist (locked 2026-05-28)

```js
const M5_HUB_KNOWN_NOT_CUSTOM = [];
```

Empty at v1. No hub-installed skills were present on the dev box at build time (`.hub/lock.json` showed `"installed": {}`). Hub-installed skills are detected automatically by the presence of `_meta.json` — this list is reserved for any future hub skills the M5 curriculum directs users to install by a specific name.

## _meta.json detection (belt-and-suspenders)

Hub-installed skills (via `hermes skills install <owner>/<slug>`) get a `_meta.json` file written by Hermes on install. User-created skills do not. The `at-least-one-custom-skill` check uses `_meta.json` presence as an additional filter beyond the two allowlists. This means newly hub-installed skills (even with slugs not in either allowlist) are correctly excluded from the custom-skill count.
