# Module 4 — Connect a Channel (Telegram)

Run: `node bin/verify.js 4`

## Deterministic checks

| ID | What it verifies | How |
|---|---|---|
| `telegram-configured` | `TELEGRAM_BOT_TOKEN` (or `HERMES_TELEGRAM_BOT_TOKEN`) is present and non-placeholder in `~/.hermes/.env` | Read `.env`, regex for `^(TELEGRAM_BOT_TOKEN|HERMES_TELEGRAM_BOT_TOKEN)=\S+`, confirm value length > 10 and not a placeholder — value is **never** logged or included in evidence |
| `gateway-bot-bound` | `hermes gateway status` reports the gateway is running and a Telegram channel is live | Parse output for "gateway not running" indicator vs Telegram + live-indicator patterns |

## Manual check

- `telegram-responds` — Send a message to your Hermes bot from your phone and confirm a reply arrives. The deterministic checks above only confirm config + gateway-side wiring — they do not prove messages actually flow end-to-end. This round-trip is the real proof.

## Security posture — NEVER log the token value

The Telegram bot token is a credential with the format `<numeric_id>:<base64-ish-string>` (~46 chars). The `telegram-configured` check:

1. Opens `~/.hermes/.env` with `readFileSafe`
2. Runs a regex that captures the variable name and value
3. Checks that `value.length > 10` and the value is not a placeholder string
4. Adds `{ var: 'TELEGRAM_BOT_TOKEN', present: true }` to evidence — the token value (`match[2]`) is **explicitly excluded**

Acceptable evidence shapes:
- Pass: `{ var: 'TELEGRAM_BOT_TOKEN', present: true }`
- Fail (missing): `{ present: false, hint: 'Run hermes gateway setup ...' }`
- Fail (placeholder): `{ var: 'TELEGRAM_BOT_TOKEN', present: false, hint: 'Run hermes gateway setup ...' }`

The token value must never appear in JSON evidence, error messages, or report output.

## Phase 0 finding — token lives in `.env`, not `config.yaml`

Per Phase 0 §2 investigation: the Telegram bot token is stored in `~/.hermes/.env`, not in `~/.hermes/config.yaml`. The `.env` file contains gateway credentials; `config.yaml` contains model provider / dashboard settings. The `telegram-configured` check reads `.env` accordingly.

## gateway-bot-bound regex design

**Probed 2026-05-28:** `hermes gateway status` output when gateway is not running:
```
✗ Gateway is not running

To start:
  hermes gateway run      # Run in foreground
  hermes gateway install  # Install as user service
  sudo hermes gateway install --system  # Install as boot-time system service
```

The check applies a three-tier logic:

1. **telegram + live indicator** (`/telegram[^\n]*?(live|running|connected|ok|active|✓|started)/i`) → PASS — Telegram is bound and live
2. **gateway running but telegram mentioned without live indicator** → FAIL — channel visible but not confirmed live; check `hermes gateway logs`
3. **gateway not running** (matched by `✗` or absence of `✓`/`Gateway is running`) → FAIL with actionable start instructions
4. **gateway running but no telegram mention** → FAIL — run `hermes gateway setup`

Config-grep alone (check 1) proves credentials exist; the live-status surface (check 2) is the real binding proof per spec §6 M4.
