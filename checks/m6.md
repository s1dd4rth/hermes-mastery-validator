# Module 6 — Crons (Pillar 4)

Run: `node bin/verify.js 6`

## Hermes cron schema (discovered 2026-05-28)

Source: `~/.hermes/hermes-agent/cron/jobs.py`

**File location:** `~/.hermes/cron/jobs.json`

**Top-level shape:**

```json
{
  "jobs": [ /* array of job objects */ ],
  "updated_at": "<ISO timestamp>"
}
```

**Job object fields (relevant to M6 checks):**

| Field | Type | Notes |
|---|---|---|
| `id` | string | 12-char hex UUID |
| `name` | string | Human-friendly label or truncated prompt |
| `schedule` | object | Nested sub-object (see below) |
| `schedule_display` | string | Human-readable schedule string |
| `enabled` | bool | `true` = active, `false` = paused |
| `state` | string | "scheduled", "paused", "completed", "error" |
| `next_run_at` | ISO string or null | null after completion or on error |
| `deliver` | string | "origin", "local", "telegram:chat_id", etc. |
| `origin` | object or null | `{ platform, chat_id, chat_name, thread_id }` |
| `repeat` | object | `{ times: int|null, completed: int }` |
| `last_run_at` | ISO string or null | |
| `last_status` | string or null | "ok" or "error" |

**schedule sub-object — three forms:**

```js
// One-shot (duration or ISO timestamp)
{ kind: "once", run_at: "<ISO>", display: "once in 30m" }

// Recurring interval
{ kind: "interval", minutes: 60, display: "every 60m" }

// Cron expression
{ kind: "cron", expr: "0 9 * * *", display: "0 9 * * *" }
```

**Key finding: no per-job timezone field.**
Hermes does NOT store a `tz` or `timezone` field on the job or the schedule sub-object. The scheduler uses `hermes_time.now()` which reads the system timezone. The `cron-schedule-and-tz` check was adapted accordingly: it verifies the schedule is present (any kind) and notes whether a timezone is configured in `config.yaml`, treating system timezone as always available (per Hermes's actual behavior).

## Deterministic checks

| ID | What it verifies | How |
|---|---|---|
| `cron-exists` | `~/.hermes/cron/jobs.json` parses and contains at least one user-created job (not in `M6_SYSTEM_DEFAULT_JOBS`) | `fs.existsSync` + `JSON.parse` + filter by `M6_SYSTEM_DEFAULT_JOBS` |
| `cron-schedule-and-tz` | The job has a recognized schedule (kind = "once", "interval", or "cron") AND the system has a timezone available | `job.schedule.kind` check + system-tz always-present assumption |
| `cron-enabled-and-bound` | The cron is enabled (`job.enabled !== false`), has a `next_run_at` timestamp, and references a real delivery channel (`job.deliver` exists and is not `"local"`) | Field presence checks on the first user-created job |

### Check chain logic

All three deterministic checks are chained. If `cron-exists` fails, the other two immediately FAIL with `{ dependent_on: 'cron-exists' }` and no further inspection is done. This is honest: `cron-schedule-and-tz` and `cron-enabled-and-bound` have no data to inspect if there are no jobs.

### Delivery channel semantics

- `"local"` — save output only, no external delivery. Treated as **unbound** for this check (the job can't prove delivery without a channel).
- `"origin"` — deliver back to the chat that scheduled the job. Treated as **bound** (it requires a real channel to have existed at schedule time).
- `"telegram:..."`, `"discord:..."`, etc. — explicit target. Treated as **bound**.

This matters because a job scheduled with `deliver: "local"` will never fire an end-to-end delivery proof, making `cron-fires-end-to-end` structurally impossible.

## Manual check

- `cron-fires-end-to-end` — "Schedule a one-shot cron for two minutes from now, wait, and confirm you receive the message in your chosen channel. The deterministic checks above only verify the job is configured to fire; this confirms the executor + channel + delivery actually round-trip."

This is the load-bearing M6 check. It exercises:
1. The cron scheduler actually ticking (not just persisting the job)
2. The executor spawning a session and running the prompt
3. The delivery pathway (Telegram, Discord, or origin chat) completing the loop

**Mac mini sleep caveat (per OpenClaw M4):** If the Mac mini sleeps or the gateway daemon is killed, the scheduler tick stops. A cron job scheduled during sleep will either be skipped (if past its grace window) or fire immediately on resume. This is not a validator bug — it's an environment-specific behavior. Ensure the gateway is running (`hermes gateway status`) before testing `cron-fires-end-to-end`.
