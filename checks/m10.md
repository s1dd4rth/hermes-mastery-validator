# Module 10 — Completion + Self-Improving Loop

Run: `node bin/verify.js 10`

## Orchestration principle: M1–M9 only (bonus-exclusion)

M10 orchestrates modules 1 through 9 only (`for (let n = 1; n <= 9; n++)`). Bonus modules (M11+) are explicitly excluded. This is the **bonus-exclusion principle** per spec §6 M10: the completion code encodes the learner's core course setup state, not optional extras. If bonus modules were included, the canonical tally would be different for learners who chose to complete bonuses vs. those who didn't — invalidating code comparisons. The loop bound is pinned at `n <= 9` forever.

## Deterministic completion code

The completion code is `HMS-` followed by the first 12 characters of the RFC 4648 base32 encoding of `sha256(canonical_tally)`.

**Canonical form:** `JSON.stringify` of the per-module tally array, where each entry has keys in fixed order: `{ module, passed, failed, manual, total }` (or `{ module, error: true }` for execution failures). **DO NOT change this key order** — it would invalidate every existing learner code.

**Same setup state → same code:** the tally counts (passed/failed/manual/total) for M1-M9 are purely a function of the learner's Hermes configuration. Running the validator twice in a row on the same machine produces identical output. The `checked_at` timestamp in the outer envelope does NOT affect the canonical tally and does NOT affect the code.

**Dev-box smoke test (2026-05-28):** `HMS-563WFZVXJP2I` — confirmed identical across two consecutive runs.

## Base32 RFC 4648 encoding (not base64)

The encoding uses alphabet `ABCDEFGHIJKLMNOPQRSTUVWXYZ234567` (standard RFC 4648 §6). Base64 is explicitly NOT used — base32 produces codes that are:
- Case-insensitive (safer for form entry)
- Free of `+`, `/`, `=` characters (no URL-escaping needed)
- Visually distinct from hex (learners can tell it's a course code, not a raw hash)

The `encodeBase32(buf)` helper lives near the other utilities in verify.js, just before `runModule10`. It processes the 32-byte SHA-256 digest and we take only the first 12 output characters (60 bits of entropy — more than sufficient for a course completion code).

## Canonical-form pinning

The canonical JSON uses this exact key order:
```js
{ module: t.module, passed: t.passed, failed: t.failed, manual: t.manual, total: t.total }
```

JavaScript's `JSON.stringify` preserves object literal insertion order (ES2015+). This is stable across all Node.js versions ≥ 12. The key order above is pinned forever — any change would produce different SHA-256 input and thus a different completion code, breaking all existing learner submissions.

## Deterministic checks (5)

### `hermes-reviewed-setup`

**How:** Run modules 1–9 as subprocesses (`node <self> <n>`). Each module's stdout must parse as valid JSON without `status !== 0`. If all 9 parse successfully, PASS; if any fail to execute (non-zero exit or JSON parse error), FAIL with a list of which modules errored.

**Note:** this check passes even if individual M1-M9 checks are FAIL or manual — it only tests that the runners executed without crashing. A learner can have a FAIL in M3 and still get `hermes-reviewed-setup: true`.

**Dev-box result (2026-05-28):** PASS — all 9 modules executed without error.

## Manual checks (2)

### `assessment-opened`

**Instruction:** Open the course assessment Google Form (linked in the M10 panel) and submit your HMS- completion code.

**Rationale:** The Google Form is the course owner's submission surface. The URL is not hardcoded in the validator (it may change) — the web app module links to it. The validator can't programmatically confirm the form was opened; this must be confirmed manually by the learner.

---

### `loop-honesty-check`

**Instruction:** Open the Hermes dashboard. Can you point at evidence of the self-improving loop: a Curator run timestamp, a session search returning a fact the agent learned about you, a Honcho user-model entry? If you cannot, M10 has *named* the loop but not *shown* it — that's a course bug, please report.

**Rationale (from spec §6 M10):** The "self-improving loop" is a core claim of the Hermes course. M10 must not just name the loop — it must show it. This check is deliberately uncomfortable: if the learner genuinely can't find evidence, they should report it as a course bug. This keeps the curriculum honest and drives improvement. A passing score on all deterministic checks but a failing loop-honesty-check is a signal the course needs better loop-visibility tooling.
